00Before You Start

Direct prerequisites for this module:

Module 06 — Sources & Sinks
Before You Start You need to be solid on Module 05's core mechanic — untrusted data interpolated into HTML with no encoding, becoming real markup. This module changes exactly one thing about that mechanic: WHEN and for WHOM the sink fires. Everything else is identical.

01The Big Analogy

Head First Moment

Module 05's attack was the waiter reading a fake announcement over the PA system the instant it was handed over — one customer, one reading, done. Module 07's attack is different: instead of reading the card aloud immediately, the waiter pins it to the restaurant's specials board, right next to today's soup and dessert options. Now every single customer who walks in for the rest of the night reads that fake announcement, just by glancing at the board — nobody had to hand THEM a fake card personally. One attacker, pinning one note, silently reaches every future customer.

Module 05 — Reflected

Attacker crafts a URL. Victim must click it. Sink fires once, for that one victim, that one time.

Module 07 — Stored

Attacker posts a comment once. Sink fires for every visitor who ever loads the page afterward — no click, no crafted link, nothing but a normal visit.

02The Same Bug, One New Ingredient

Compare this module's rendering function to Module 05's. Structurally, it's the same missing-encoding bug — but now it runs inside a loop over stored data:

function renderGuestbook() {
  const commentsHtml = comments
    .map((c) => `<div><strong>${c.name}</strong>: ${c.message}</div>`) // same bug as Module 05, now per-comment
    .join('\n');
  return `...${commentsHtml}...`; // runs for EVERY visitor who loads this page
}

The write side is just as important. Here's the entire storage step — notice there is no encoding call anywhere near it either:

comments.push({ name: params.name, message: params.message }); // stored exactly as submitted, untouched
Why this matters A common (and wrong) intuition is "the bug is in how the comment gets stored." It isn't. Storage is just a pipe — completely inert whether it's an array, a file, or a real database. The bug is 100% in the render step, exactly where Module 05's bug was. Storage just changes the blast radius from "one victim who clicked a link" to "every visitor to this page, indefinitely."

03Run It on Windows 11

Terminal 1
cd xss_mastery\modules\07_stored_xss_via_post
.\run.ps1 -Target run-node
Terminal 2 — post a malicious comment as "the attacker"
curl -X POST http://localhost:8000/comment \
  --data-urlencode "name=attacker" \
  --data-urlencode "message=<script>alert(document.cookie)</script>"
Now — as a completely fresh, unsuspecting visitor
Open http://localhost:8000/ in your browser. Just that URL. No query string,
no special link, nothing crafted -- exactly what a normal visitor would type.
Expected result
The page loads and immediately pops an alert() showing your cookies --
even though YOU never typed a malicious payload anywhere. The attacker's
comment, posted once, attacked you on a completely ordinary page visit.
If you have PHP installed
.\run.ps1 -Target run-php
