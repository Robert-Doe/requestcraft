01The Big Analogy

Head First Moment

A careless kitchen inspector checks one dish, sees it's fine, and signs off on the whole menu. A real inspector brings a checklist — every category of thing that's gone wrong at restaurants before (temperature, cross-contamination, storage, labeling) — and tests each category specifically, not just whatever dish happens to be on the counter that day. Module 16 is that checklist, mechanized: instead of trying one payload and declaring victory, you sweep a whole catalog of DIFFERENT categories of attack against a target and actually look at what comes back, not just whether your one original guess vanished.

02A Target That Looks Fixed and Isn't

The test target's entire "defense" is one line:

function naiveFilter(q) {
  return q.replace(/script/gi, ''); // removes the WORD "script" -- once, non-recursively
}

Tried against the textbook payload, it looks like it works:

sent:      <script>alert(1)</script>
reflected: <>alert(1)</>         // broken tag -- doesn't execute
Why this matters A tester who stops here concludes "fixed." This is precisely the mistake this module exists to train out of you.

05Brain Exercise

Brain Exercise

Look again at the javascript-href row: the tool flagged it "verify manually" because <a href=...> survived intact. Manually inspect what actually got reflected: <a href="java:alert(1)">. Is this payload actually dangerous, or was the tool being overly cautious?

In this specific instance, it's actually neutralized — "java:" is not a recognized URL scheme, so nothing executes. The filter accidentally broke javascript: into java: the same way it accidentally broke <script> into <> — same bug, different sink, this time landing in "safe" by coincidence rather than design. This is exactly why the tool's verdict is phrased as "verify manually" instead of "confirmed dangerous": a mechanical pattern match (does a tag survive?) is a reasonable FIRST filter for what deserves a closer look, but it cannot by itself distinguish "survived AND dangerous" from "survived AND happens to be harmless." That distinction requires actually reading what remains — precisely the step a rushed tester skips, and precisely the step this module is training you to never skip. Notice also that this accidental "safety" is not something you should ever rely on or recommend — it's a coincidence of one specific filter's bug, not a real defense, and a differently-worded payload could easily avoid it entirely.

06There Are No Dumb Questions

Q: Is this how real automated security scanners work?
A: At a basic level, yes — this is a simplified version of the same core loop real tools (Burp Suite's active scanner, OWASP ZAP, custom fuzzers) use: send known-shape payloads, inspect the response, classify. Real tools add far more sophistication (browser-based execution verification via headless browsers, response diffing across many payloads, context-aware payload selection based on where a value seems to land) — but the underlying loop, and the underlying discipline of not trusting "it looks different now," is the same.
Q: Why not just render every response in a real headless browser and check if a global flag got set, like this course's own earlier verification steps did?
A: That's genuinely a more reliable verification technique than text-pattern classification (and it's exactly what this course did to verify Modules 05, 07, 08, and others) — it directly answers "did the script execute" instead of inferring it from the markup shape. It's also heavier: it requires a real browser engine and more infrastructure than a plain HTTP client. Text-based classification is the right first-pass tool for sweeping a large catalog quickly; browser-based confirmation is the right tool for verifying a specific, high-confidence finding.
Q: Should I trust a payload catalog I find online, copy-pasted wholesale?
A: Use it as a starting point, not a checklist to blindly run through — the actual skill this module is teaching is recognizing WHY each payload category matters (different sink, different bypass technique, different encoding assumption) so you can adapt and extend the list for whatever specific target you're actually testing, the same way this module's eight entries were chosen for category coverage rather than volume.
