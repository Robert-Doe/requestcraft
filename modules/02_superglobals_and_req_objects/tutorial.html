02What "Superglobal" Actually Means

A superglobal (PHP's term for a built-in array that's automatically available inside every function, with no need to import or declare it) isn't magic — it's PHP's SAPI (the layer that connects PHP to a web server) doing the exact byte-splitting job you'd otherwise have to do by hand, and handing you the result before your script's first line even runs. Node makes the same job explicit rather than automatic: the http module hands you a raw req object, and you (or a library) still have to parse req.url's query string and read req's body stream yourself — which is precisely why Module 02 has you write that parser by hand once, so you know exactly what PHP is doing for you invisibly.

Why this matters Once you've hand-written parseFormEncoded() yourself, a superglobal stops looking like magic and starts looking like exactly what it is: a `split` on &, a `split` on =, and a percent-decode. Every time you later wonder "wait, how did this value get into $_GET," you now have a real mental model to check it against, instead of a black box.

03Parsing a Query String by Hand

Here's the core of parseFormEncoded() from node/server.js — the same logic PHP's SAPI runs for you before you ever see $_GET:

function parseFormEncoded(text) {
  const result = {};
  if (text === '') return result; // nothing to parse -- avoid a bogus {'': ''} entry

  for (const pair of text.split('&')) {
    const eqIndex = pair.indexOf('=');
    const rawKey = eqIndex === -1 ? pair : pair.slice(0, eqIndex);
    const rawValue = eqIndex === -1 ? '' : pair.slice(eqIndex + 1);

    // '+' means literal space in this encoding -- must happen before percent-decoding
    const key = decodeURIComponent(rawKey.replace(/\+/g, ' '));
    const value = decodeURIComponent(rawValue.replace(/\+/g, ' '));

    result[key] = value; // later keys overwrite earlier ones -- see DECISIONS.md #3
  }
  return result;
}

And the PHP side of the same story — notice there's no parsing code at all, because it already happened before this script started:

$dump = [
    'method' => $_SERVER['REQUEST_METHOD'], // superglobal -- no parsing code visible here
    'GET'    => $_GET,                     // already parsed by the SAPI before this line runs
    'POST'   => $_POST,                    // same -- but only for form-encoded/multipart bodies (see DECISIONS.md #4)
];
Why this matters The PHP snippet is short because the work is invisible, not because there's less work happening. That invisibility is exactly why PHP beginners get surprised the first time they POST JSON and find $_POST empty (DECISIONS.md #4) — the parsing didn't fail, it simply never runs for content types PHP doesn't recognize as a form.

05Brain Exercise

Brain Exercise

Run this against the Node server:

curl "http://localhost:8000/search?q=hello&q=world"

What do you expect GET.q to be in the response — an array of both values, or just one of them?

It'll be "world" — just the last one, silently overwriting the first. Look back at parseFormEncoded(): the line result[key] = value has no check for whether key already exists. This isn't a bug you're meant to panic about — DECISIONS.md #3 names it as a deliberate simplification — but it IS a real trap if you ever build a form with a multi-select field and wonder why only one selection survived. PHP's actual `$_GET`/`$_POST` have the exact same overwrite behavior for a plain repeated key like ?q=hello&q=world — PHP only collects multiple values when you use the explicit `?q[]=hello&q[]=world` bracket syntax. The trap here is realistic, not invented.

06There Are No Dumb Questions

Q: If $_GET and $_POST are "superglobals," are they global variables I could accidentally overwrite?
A: Yes, technically — very old PHP code sometimes did exactly that by accident, which is part of why a long-removed setting called `register_globals` (which auto-created a regular variable for every request field) was considered dangerous enough to be removed from the language entirely. Treat superglobals as read-only input, never as scratch variables.
Q: My Node server needed 40 lines to do what PHP does in zero lines. Doesn't that mean PHP is just better here?
A: It means PHP made a framework-level decision to auto-parse forms for you, and Node's core `http` module deliberately doesn't — Node expects you to reach for a parsing library (or, in this course, write one) when you need it. Neither choice is "better"; they're different defaults. You'll see the cost of PHP's invisible convenience in Module 04, when a value you didn't expect to be there shows up anyway.
Q: Why does the tutorial keep warning me not to merge GET and POST together? What's actually at risk?
A: Nothing breaks today. But starting in Module 09 (CSRF), you'll see attacks that specifically exploit the fact that a GET request can be triggered by any page on the internet (via an image tag, a link, a redirect) while a POST at least requires a deliberate form submission. Code that reads from a merged $_REQUEST-style bag can no longer tell which channel a value arrived through — and that distinction is exactly what a CSRF defense needs to check.
Q: Is percent-decoding a security thing I should worry about?
A: Keep this question in your back pocket — you're right to notice it, but it's not this module's concept. Percent-decoding done at the wrong layer, or done twice, is a real source of filter-bypass bugs (a payload that looks safe once-decoded can decode again into something dangerous). You'll see this become concrete once you're building defenses in Module 11.
