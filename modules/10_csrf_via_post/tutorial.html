01The Big Analogy

Head First Moment

Module 09's stranger scanned your loyalty card through a window without you noticing. A reasonable-sounding fix: "require the card to be physically inserted into a reader, not just scanned nearby" — like upgrading from a wave-and-go GET to a deliberate insert-and-confirm POST. That should stop drive-by scanning... except the attacker just builds their OWN card reader, wires it to auto-insert your card the instant you walk near it, and triggers it themselves. The "more deliberate" mechanism didn't require MORE from the attacker — it just required a slightly different tool, one that's just as easy to build.

An auto-submitting HTML <form> is that attacker-built card reader. It performs the exact same "deliberate" POST submission a real user would make by clicking a button — except a tiny <script> clicks it for them, invisibly, the instant the page loads.

bank-vulnerable (POST-only "fix")

Requires POST. Checks nothing else. The attacker's auto-submit form defeats it completely: $1000 → $750.

bank-fixed (token + SameSite)

Same attacker page, unchanged. Server rejects with 403. Balance stays exactly where it was: $1000.

02The Attack That Still Works

Here's the entirety of the attacker's page against the naive POST-only bank:

<form id="csrf-form" method="post" action="http://localhost:8000/transfer" style="display:none">
  <input name="to" value="attacker">
  <input name="amount" value="250">
</form>
<script>
  document.getElementById('csrf-form').submit(); // fires instantly -- no click, no visible UI
</script>

And the bank's entire remaining vulnerability:

if (req.method !== 'POST') { /* reject */ }
// nothing else checks WHERE this POST came from, or requires anything
// the attacker couldn't already know -- session cookie is enough
balances[session] -= amount;

03The Real Fix, Two Layers

Layer 1 — a CSRF token the attacker's page cannot know:

// issued once per session, embedded as a hidden field in the LEGITIMATE form only
csrfTokens[session] = crypto.randomBytes(16).toString('hex');

// checked on every transfer -- the attacker's forged form has no way to know this value
if (params.csrf_token !== csrfTokens[session]) {
  return res.writeHead(403).end('Forbidden');
}

Layer 2 — a cookie the browser itself refuses to send cross-site:

res.setHeader('Set-Cookie', 'session=victim; Path=/; SameSite=Strict');
// tells the BROWSER: never attach this cookie to a request that
// originated from a different site -- enforced before your code even runs
Verified This course tested both bank variants against the identical, unmodified attacker page. The naive POST-only version lost $250 silently. The token+SameSite version logged REJECTED -- csrf_token mismatch (got undefined) and the balance never moved. Same attack, two different codebases, two different outcomes — the code, not the attacker, is what changed.

05Brain Exercise

Brain Exercise

A teammate asks: "If SameSite=Strict alone stops the browser from sending the cookie cross-site, why bother with the CSRF token at all? Isn't one defense enough?"

Because the two defenses fail independently, and "enough" depends on trusting exactly one mechanism to never have a gap. SameSite is enforced by the BROWSER — it's only as strong as every browser your users might have, correctly implementing the spec, with no bugs, with no legacy fallback behavior for older clients your app still needs to support. A CSRF token is enforced by YOUR SERVER — it works the same way regardless of which browser, or browser version, or non-browser HTTP client, is making the request. History has real examples of both categories failing alone: browser SameSite bugs and inconsistencies (exactly the kind this course found empirically while building this module), and CSRF-token implementations with subtle validation bugs (Decision #4 in this module's DECISIONS.md names a real one — checking "does a token field exist" instead of "does it match"). Depending on exactly one layer means a single flaw in that one layer is a complete bypass. Depending on two independent layers means an attacker needs both to fail at once.

06There Are No Dumb Questions

Q: Does a CSRF token need to be secret the way a password is?
A: It needs to be unguessable and never exposed to a page the attacker controls — but unlike a password, the LEGITIMATE page is allowed to embed it directly in HTML the user's own browser renders, because the attacker's separate page has no way to read content from a page it doesn't control (this is exactly what the Same-Origin Policy DOES protect, unlike the request-sending question from Module 09's Brain Exercise).
Q: Do GET requests need CSRF tokens too?
A: A well-designed GET request shouldn't need one, because Module 04 already established that GET must never change state — CSRF tokens exist specifically to protect state-changing actions. If you find yourself wanting to add a CSRF token to a GET endpoint, that's usually a sign the real bug is Module 04's, not this module's: the GET endpoint shouldn't be mutating anything in the first place.
Q: Can an API that uses a header-based auth token (not cookies) be CSRF'd?
A: Generally no, and this is worth understanding precisely why: CSRF works because the BROWSER automatically attaches cookies to every request to a given domain, with no action from attacker-controlled JavaScript required. A custom header (like `Authorization: Bearer `) is never attached automatically by the browser — the attacker's page would have to explicitly set that header via JavaScript, which triggers a CORS preflight check that the bank's server would have to explicitly allow. This is exactly why many modern APIs prefer bearer tokens in headers over cookies specifically to sidestep CSRF as a category, at the cost of needing to manage token storage on the client themselves (usually with its own trade-offs around XSS exposure, since a token in JavaScript-accessible storage is readable by exactly the kind of script Module 05-08 taught you to inject).
