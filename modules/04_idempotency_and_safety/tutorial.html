Idempotency & Safety

A counter that goes up before you've clicked anything — and one that doesn't.

01The Big Analogy

Head First Moment

Imagine a restaurant where simply glancing at the dessert menu somehow triggered the kitchen to bake you a cake. Every food critic who walks by, every health inspector doing a routine look-around, every curious passerby peeking through the window — all of them would accidentally cause cakes to get baked, whether they wanted one or not, just by looking. That's insane, because looking at a menu is supposed to be a "safe" act with no consequences. Nobody expects glancing at something to change the kitchen's state.

A GET request is that glance. RFC 7231, the specification that defines HTTP methods, literally calls GET a "safe" method — safe specifically meaning it's not supposed to change anything on the server. Browsers, crawlers, link-preview bots, and antivirus scanners all rely on that promise being true, and they issue GET requests constantly and automatically, without asking anyone's permission, because a "glance" is supposed to be free.

The unsafe counter

A plain GET to /unsafe-increment changes server state. Anything that can issue a GET — a link click, a hidden image, a bot — can silently bake the cake.

GET /unsafe-increment → count++

The safe counter

Only a POST to /safe-increment changes state. A GET to the same path gets flatly rejected with 405 — no accidental cake.

POST /safe-increment → count++

02The Bug, in One Line

Here's the entire vulnerable route from node/server.js:

if (path === '/unsafe-increment' && req.method === 'GET') {
  unsafeCount += 1; // the entire bug lives in this one line responding to GET
  res.writeHead(302, { Location: '/' }); // redirect back so a real click "just works"
  res.end();
  return;
}

And the page that ships alongside it contains this, completely hidden from view:

<!-- fires a real GET the instant this page loads -- zero clicks required -->
<img src="/unsafe-increment" style="display:none" alt="">
Why this matters This isn't a hypothetical. Real applications have shipped account-deletion or logout actions as plain <a href="/logout"> links — and antivirus software or link-preview bots that pre-fetch every URL on a page have logged users out, or worse, purely by "looking." The fix is never "make the crawler smarter." The fix is always "GET must not change anything," full stop — you cannot negotiate with a search engine's crawler.

03The Fix, Side by Side

The safe counter's route checks the method and refuses anything that isn't POST:

if (path === '/safe-increment') {
  if (req.method !== 'POST') {
    // fail LOUDLY -- silently ignoring the GET would hide the lesson
    res.writeHead(405, { 'Content-Type': 'text/plain' });
    res.end('405 Method Not Allowed -- this endpoint only accepts POST, on purpose\n');
    return;
  }
  safeCount += 1;
  // ... redirect back, same as the unsafe route
}

Notice the safe version needs a real <form method="post"> to trigger it — there is no HTML tag that fires an automatic POST on page load the way <img> fires an automatic GET. That asymmetry is not an accident of HTML design; it's the direct, practical consequence of GET being declared "safe" and POST not being declared safe.

05Brain Exercise

Brain Exercise

Suppose a teammate "fixes" the unsafe counter like this, without changing the route's HTTP method at all:

<a href="/unsafe-increment" onclick="return confirm('Are you sure?')">
  Click to increment
</a>

They argue: "Now the user has to confirm before it happens, so it's safe." Does this actually fix the vulnerability this module demonstrated?

No — and the crawler you just ran proves it in one sentence: the hidden <img src="/unsafe-increment"> never went through that <a> tag at all, so the confirm() dialog never runs for it. A JavaScript confirmation only intercepts clicks on that specific element — it does nothing to stop a request issued by an <img> tag, a crawler, a prefetcher, or literally anyone typing the URL directly into a browser or curl. The confirmation dialog is a UI nicety layered on top of a link; it is not a property of the URL itself, and the URL is still just as "safe to GET with no side effects, right?" to everything that isn't a human reading a JavaScript dialog box. The only real fix is the one this module made: refuse to mutate state on anything but POST.

06There Are No Dumb Questions

Q: Couldn't I just block known bots by checking the User-Agent header?
A: No — User-Agent is just a string the client sends you, and it's trivial to fake or omit. More importantly, this module's own hidden `` tag proves the attack doesn't require a "bot" at all: an ordinary human's ordinary browser, loading an ordinary page, fires the GET. There's no User-Agent to distinguish, because the "attacker" is just... a web page.
Q: Is DELETE or PUT automatically safe from this, since they're not GET?
A: DELETE and PUT are not "safe" per RFC 7231 either — only GET, HEAD, OPTIONS, and TRACE are. But DELETE and PUT ARE idempotent (calling them twice has the same effect as calling them once), which GET is also supposed to be. The property this module cares about most is "safe" specifically — the guarantee that simply fetching a resource causes no side effect — and only GET (and HEAD) carry that guarantee. PUT and DELETE are expected to change things; the difference is that browsers, crawlers, and `` tags don't issue PUT or DELETE automatically the way they issue GET.
Q: If this is such a well-known problem, why does it still happen in real apps?
A: Usually because a GET-triggered action feels convenient during development — a plain link is less code than a form and a POST handler — and the bug doesn't announce itself until a crawler, an email client's link-preview feature, or a corporate security scanner stumbles onto the URL. It's a bug that's invisible until exactly the kind of automated GET-issuing tool this module simulated shows up.
