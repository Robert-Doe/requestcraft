xss_mastery · Module 08

DOM-Based XSS

The server is innocent this time. The entire bug lives in the browser.

00Before You Start

Direct prerequisites for this module:

Module 07 — Stored XSS via POST
Before You Start You need Module 06's sink vocabulary solid — recognize .innerHTML as dangerous, .textContent as not, on sight. This module's twist isn't a new sink; it's a source that never goes near a server.

01The Big Analogy

Head First Moment

Every attack so far involved the kitchen somehow — a ticket reaching it (POST), an announcement being read from something the front door heard (GET). Module 08 is different: imagine a customer scrawling a note directly on a table's own little order-status display — a screen sitting right there at the table that just shows "your order status," which the CUSTOMER'S OWN PHONE updates locally without ever contacting the kitchen. If the display blindly shows whatever text is typed into it, a customer can make their own table's screen say anything they want — and the kitchen never finds out, because the kitchen was never involved in the first place.

That local display is your browser's DOM. location.hash is the note the customer wrote. Nothing about this interaction ever reaches "the kitchen" (your server) — the entire vulnerable read-and-render cycle happens on one device, in one browser tab.

02The Vulnerable Script, Line by Line

function updateGreeting() {
  var name = location.hash.substring(1);       // everything after '#' -- NEVER sent to any server, ever
  var decoded = decodeURIComponent(name);     // readability only -- does NOT make this safe (see DECISIONS.md #4)
  document.getElementById('greeting').innerHTML =
    'Hello, ' + decoded + '!';       // THIS is the sink -- same kind of bug as Modules 05 and 07
}
window.addEventListener('hashchange', updateGreeting); // re-runs on every in-page hash change, no reload needed
updateGreeting();                                     // also runs once immediately for whatever hash was present on load
Why this matters location.hash exists specifically so a page can react to changes without asking the server for anything — that's WHY single-page apps use it for client-side routing. The same property that makes it efficient (no round-trip) is exactly what makes this bug invisible to any tool that only inspects server-side code or network traffic for the payload itself.

Expected result
An alert() pops up immediately -- your JavaScript ran, sourced entirely

before the '#' -- everything after '#' never appears in ANY request.

Note: because this specific payload uses <img src=x onerror=...>, you'll actually see ONE extra request in the Network tab: GET /x, returning 404. That's the browser trying (and failing) to load the broken image "x" -- it's what triggers onerror. Look closely: that request carries none of the payload. It's an artifact of this payload's trigger mechanism, not a leak of your attack string.

04Brain Exercise

Brain Exercise

You just read, in the box above, that triggering this exact payload causes one extra network request (GET /x → 404) even though the module's whole premise is "zero server round-trip." Does that extra request mean the module's core claim is wrong?

No — and the distinction is exactly the point. The claim was never "this payload causes literally zero network activity, no matter what." The claim is specifically about the SOURCE: location.hash itself is never transmitted in any HTTP request, under any circumstances — that's a structural property of URL fragments, guaranteed by the URL specification, not an accident of this one payload. The GET /x request you saw is a side effect of THIS payload's chosen trigger mechanism (a deliberately broken image, used only to fire onerror) — inspect that request and you'll find it carries zero trace of your actual attack string. A different payload — one that doesn't need to reference any external resource to execute — would produce no extra request at all, while still being exactly as dangerous. The lesson: verify precisely what a claim is about before either believing it or debunking it. "The hash isn't sent to the server" and "this specific proof-of-concept causes zero network activity of any kind" are two different claims, and only the first one is what this module actually asserts.

05There Are No Dumb Questions

Q: If the server never sees this, can server-side logging or a WAF (web application firewall) ever catch this attack?
A: No, structurally — a WAF inspects requests as they arrive at (or in front of) your server, and this payload is never part of any request. This is one of the clearest illustrations of why server-side defenses alone are never a complete XSS strategy — Module 12's Content-Security-Policy is a defense that DOES work here, because it's enforced by the browser itself, on the page, regardless of where the dangerous value came from.
Q: Does this mean query strings (?q=) are safe from DOM-based XSS since they're at least visible to the server?
A: Not at all — `location.search` (which reads the query string) is just as available to client-side JavaScript as `location.hash` is. The server SEEING a value doesn't stop client-side code from ALSO reading that same value out of the URL and mishandling it in the exact same way this module demonstrates. "Visible to the server" and "safe" are unrelated properties.
Q: Is DOM-based XSS newer or rarer than reflected/stored XSS?
A: It's not newer, but it's become far more common as applications shifted more logic into client-side JavaScript (single-page apps, client-side routers, heavy DOM manipulation). Every framework that manipulates the DOM based on URL state — which is most modern JavaScript frameworks — has this exact category of risk somewhere in its routing layer if a developer bypasses the framework's built-in escaping.
