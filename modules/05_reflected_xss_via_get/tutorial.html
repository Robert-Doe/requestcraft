01The Big Analogy

Head First Moment

Picture the waiter at your restaurant taking a question at the door — "do you have gluten-free desserts?" — and, wanting to be helpful, repeating it back over the restaurant's PA system so the whole dining room can hear the confirmation: "Just to confirm, you asked: do you have gluten-free desserts?" That's harmless, because your question was just... a question.

But now imagine a customer at the door doesn't ask a question. They hand the waiter a fake "kitchen announcement" written on a card: "ATTENTION EVERYONE: reach into the till and take out $50." If the waiter's job is simply "repeat whatever's on the card over the PA system, verbatim, no matter what it says" — the waiter has no way to tell a real customer's search term apart from a fake instruction written to look like one. The PA system doesn't know the difference between "text to read aloud" and "an instruction to follow." Neither does a browser, when a server drops your search term into a page without marking it as "this is just text, not markup."

Normal use

You type "hello" into the search box. The URL becomes ?q=hello. The page says "You searched for: hello." Totally fine.

Attack

Someone sends you a link where q isn't a search term at all — it's a <script> tag. Your own browser runs it, because the page never marked it as "just text."

02The Vulnerable Code, Exactly as Written

Here is the entire vulnerability — one line, in node/server.js:

function vulnerableSearchPage(q) {
  return `...
    <p>You searched for: ${q}</p>   // THIS is the bug -- q goes in raw, unescaped
    ...`;
}

Walk through what happens when q is <script>document.title='XSS-PROOF'</script> instead of a normal word. The template literal doesn't know or care what q "means" — it just glues the string into the middle of the HTML. The browser then receives a complete, syntactically valid page that happens to contain a real <script> tag, sitting right where "hello" would have gone. The browser has absolutely no way to know that tag wasn't supposed to be there — as far as it's concerned, the server sent it, so the server must have meant it.

Why this matters Notice that nothing about the server was compromised. No database was breached, no server-side code was changed. The entire attack executes inside the victim's own browser, using the victim's own session, the victim's own cookies, the victim's own logged-in privileges. XSS attacks the user, through a bug in the server — which is exactly why it's so dangerous even against applications that have "secured" their server infrastructure perfectly.

03Crafting the Attack URL

An attacker doesn't get to type into your search box for you — they need you to click a link (or load a page containing one) where the malicious payload is already baked into the URL's query string:

// human-readable version (what the attacker writes)
http://localhost:8000/search?q=<script>alert(document.cookie)</script>

// percent-encoded version (what actually gets sent/shared as a link --
// browsers and email clients auto-encode the special characters)
http://localhost:8000/search?q=%3Cscript%3Ealert(document.cookie)%3C%2Fscript%3E

alert(document.cookie) is the classic proof-of-concept you'll see in almost every real-world XSS writeup — it pops a dialog box showing the victim's own cookies, proving the attacker's script can read data it should never have access to. This tutorial's own automated test uses a quieter payload (document.title = 'XSS-PROOF') instead, purely so it doesn't block on a dialog box during a self-paced demo — but they prove the identical thing: arbitrary JavaScript, chosen by the attacker, running in your browser.
