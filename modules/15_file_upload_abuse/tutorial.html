File Upload Abuse

A file that lies about what it is, and a server that believed it.

00Before You Start

Direct prerequisites for this module:

Module 14 — Input Validation as Defense-in-Depth
Before You Start You need Module 14's allowlist-vs-blocklist distinction solid — this module applies the identical principle to file uploads: never trust a label (filename, Content-Type) when you can check the actual thing (file bytes) instead.

01The Big Analogy

Head First Moment

Imagine a delivery arrives at the restaurant labeled "FRESH PRODUCE" in the sender's own handwriting, on a box the sender packed themselves. A careless receiving clerk checks the label, sees "produce," and wheels it straight into the walk-in without opening it. A careful clerk opens every box and looks at what's actually inside, regardless of what the label claims — because the label was written by whoever sent the box, and they had every reason in the world to write whatever gets it past the door.

A file's claimed extension and its claimed Content-Type are both exactly that label — written entirely by whoever is uploading the file. Only the file's actual bytes are the box's real contents.

02The Attack, Verified

StepCommandVerified result
1Create a file evil.php containing <?php echo 'hacked'; ?>—
2curl -F "avatar=@evil.php;type=image/png;filename=evil.php" /upload-vulnerableSaved as evil.php (trusted claimed extension + Content-Type: image/png)
3Check the uploads folderThe real PHP file, extension intact, sitting exactly where it was saved
4Same exact upload, against /upload-fixed415 Unsupported Media Type — rejected outright

The vulnerable route's entire mistake:

// THE VULNERABILITY: trusts the claimed name AND claimed type completely
const safeName = baseName(avatar.filename); // only strips path separators -- NOT a content check
fs.writeFileSync(path.join(VULN_DIR, safeName), avatar.data);

The fix checks what the file actually IS, byte for byte:

const MAGIC_BYTES = [
  { ext: 'png', sig: Buffer.from([0x89, 0x50, 0x4e, 0x47]) }, // real PNGs start with these exact bytes -- always
  { ext: 'jpg', sig: Buffer.from([0xff, 0xd8, 0xff]) },
];

function detectRealImageType(data) {
  for (const { ext, sig } of MAGIC_BYTES) {
    if (data.subarray(0, sig.length).equals(sig)) return ext; // checks the DATA, not the label
  }
  return null; // not a recognized image, no matter what it claims to be
}
Verified The exact same spoofed file (PHP content, claiming to be a PNG) was tested against both routes. The vulnerable route saved it, extension intact, with its full PHP source readable on disk. The fixed route rejected it with 415. A genuinely valid PNG (real magic bytes) was then tested against the fixed route and was accepted, saved under a random server-generated name.
Why this matters Nothing about the HTTP request told the server the truth — the Content-Type field of a file part is just text the uploader typed, exactly like the filename. Believing either one is exactly the blocklist mistake from Module 14, applied to a new kind of field: trusting a claim instead of checking the thing itself.

04Brain Exercise

Brain Exercise

A teammate proposes: "Let's fix the vulnerable route by rejecting any upload whose filename ends in .php, .php5, .phtml, or .phar." Where does this run into the exact same problem Module 14 already demonstrated?

It's a blocklist over file extensions — the exact same shape of mistake as Module 14's /blocklist route, just applied to a different field. It requires enumerating every dangerous extension in advance, on every server configuration you might ever deploy to. Depending on the hosting environment, executable-treated extensions can include far more than the obvious ones: .pl, .cgi, .asp, .aspx, .jsp, .htaccess (which isn't even a script but can reconfigure how a whole directory is served), and server-specific variants like .phtml3 that a misconfigured Apache might still execute. A blocklist has to win every time; an attacker only has to find ONE extension the list forgot. The magic-byte allowlist this module actually implements doesn't care what extension is claimed at all — it only accepts content that's structurally a real image, which no amount of extension renaming changes.

05There Are No Dumb Questions

Q: Does checking magic bytes mean the file is 100% safe to serve?
A: It means the file is genuinely a well-formed image CONTAINER — it does not mean the image is free of exploits targeting bugs in whatever library later decodes it (real vulnerabilities have existed in image-parsing libraries triggered by maliciously crafted, but format-valid, image files). Magic-byte checking closes the specific door this module demonstrates (arbitrary file type disguised as an image); it is one layer, not a complete guarantee.
Q: Why generate a random filename instead of just keeping the original name but forcing the correct extension?
A: Because the original filename itself is still attacker-controlled text, and "just fix the extension" leaves every other character an attacker chose sitting in your filesystem path — a needless source of encoding, length, or special-character bugs in whatever code later reads that filename. Discarding it entirely and generating a fresh name removes that entire surface, at the minor cost of needing a separate, safely-encoded field if you want to show the user their original filename later.
Q: Should uploaded files ever be stored in a location a web server would execute?
A: No — a defense-in-depth best practice this module didn't need to implement to make its point: store uploads outside the web root entirely, or in a directory explicitly configured to never execute scripts regardless of extension. That way, even a file that somehow evaded content validation still can't run as code, because the serving configuration refuses to execute anything in that location at all.
