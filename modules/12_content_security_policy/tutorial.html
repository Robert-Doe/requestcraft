01The Big Analogy

Head First Moment

Every defense so far has been about training the waiter to read order slips correctly. Content-Security-Policy is different: it's a standing house rule, posted at the PA system itself, that says "this PA system will only ever broadcast pre-approved announcements from the manager's office — it will physically refuse to read anything handed to it live at the counter, no matter who wrote it or what it says." Even if a fake announcement slips past the waiter untrained, unnoticed, exactly as written — the PA system itself refuses to say it aloud, because it was never pre-approved.

02Three Identical Bugs, Three Different Outcomes

RouteHeaderVerified result
/no-csp(none)document.title became "NOCSP-EXECUTED" — script ran
/csp-strictscript-src 'self'title stayed as the page's own title — script blocked
/csp-unsafe-inlinescript-src 'self' 'unsafe-inline'document.title became "UNSAFE-INLINE-EXECUTED" — script ran again

All three routes serve the byte-for-byte identical vulnerable line:

<p>You searched for: ${q}</p>   // still unescaped, still Module 05's exact bug

The only difference between "executed" and "blocked" is one response header:

// csp-strict:
res.setHeader('Content-Security-Policy', "default-src 'self'; script-src 'self'");

// csp-unsafe-inline -- quietly re-opens the exact hole:
res.setHeader('Content-Security-Policy', "default-src 'self'; script-src 'self' 'unsafe-inline'");
Verified All three outcomes above were tested live, with the identical payload (<script>document.title='...'</script>) against all three routes. Only the strict policy actually blocked execution.
Why this matters 'self' means "only scripts loaded FROM this exact origin, as separate script files." An inline <script> block has no origin of its own — it's just text sitting inside the HTML — so under a strict policy, the browser refuses to run it categorically, regardless of whether that text came from your own template or an attacker's injected payload. 'unsafe-inline' is a named escape hatch that says "actually, do trust inline script text after all" — which un-does exactly the protection that mattered.

04Brain Exercise

Brain Exercise

A team ships `script-src 'self'` and calls the XSS bug "mitigated," closes the ticket, and never touches Module 05's actual encoding bug. Six months later, someone adds a new feature: a JSONP-style endpoint at /api/callback?cb=someFunctionName that's also hosted on the same origin — same site, same `'self'`. Does the original, still-unfixed reflected XSS bug remain "mitigated"?

Not necessarily — and this is a real, documented category of CSP bypass, not a hypothetical. `'self'` trusts EVERY script hosted on the same origin, including any endpoint that happens to return attacker-influenceable JavaScript — a JSONP callback whose function name comes from a query parameter is a classic example, because the attacker controls part of what gets executed, and it's still "from 'self'" as far as CSP is concerned. This is precisely why Module 11's fix and Module 12's CSP are described as two INDEPENDENT layers, not "either one is enough." The original encoding bug was never actually gone — it was dormant, waiting for any new same-origin endpoint that could be abused to smuggle attacker-influenced execution back in under the umbrella of `'self'`. Closing the ticket without fixing Module 05's actual bug left a live vulnerability sitting behind a lock that a completely unrelated, future feature accidentally picked.
