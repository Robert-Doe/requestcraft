Input Validation as Defense-in-Depth

Asking "is this on my list?" beats asking "does this look bad?" — but only sometimes.

00Before You Start

Direct prerequisites for this module:

Module 11 — Output Encoding Defenses

01The Big Analogy

Head First Moment

Imagine a restaurant's order slip has a "spice level" field that should only ever say "mild," "medium," or "hot." A blocklist bouncer checks incoming slips for obviously rude words and waves everything else through. An allowlist host does something completely different: they don't look for what's WRONG — they check the slip against the exact three words that are RIGHT, and reject anything that isn't one of them, no matter how innocent-looking. The bouncer has to imagine every possible bad word in advance and will always miss ones nobody thought of. The host doesn't need to imagine anything — there are only three acceptable answers, and everything else, seen or unseen, gets the same treatment.

02Two Validators, Same Payload

The blocklist checks for one specific bad pattern:

const isRejected = /<script/i.test(order); // only catches THIS one pattern

The allowlist checks against the only two values that should ever be valid:

const safeOrder = (order === 'asc' || order === 'desc') ? order : 'asc'; // anything else silently becomes the safe default
RoutePayloadVerified result
/blocklist<img src=x onerror=alert(1)>passed straight through, unescaped, in the raw response
/allowlistsame payloadsilently replaced with "asc" — payload never reaches the page at all
Verified curl against /blocklist with that exact payload returned Sort order: <img src=x onerror=alert(1)> — raw, unescaped, ready to execute in a browser. The identical payload against /allowlist returned Sort order: asc — completely inert, regardless of what the attacker sent.
Why this matters The blocklist's check ONLY knows about the literal substring <script. It has no idea onerror, onload, javascript:, or a hundred other execution techniques exist. Every blocklist is a bet that you've thought of every dangerous pattern in advance — and Module 07 already showed that bet losing. The allowlist makes no such bet: it doesn't need to know what's dangerous, because it only ever accepts two specific strings it already knows are fine.

03Where Allowlisting Can't Reach

The /freetext route has no allowlist at all — because none is possible:

// how would you enumerate every legitimate comment a human might write?
const msg = params.msg ?? '';
res.end(page('freetext', `<p>Message: ${encodeHtml(msg)}</p>`));

For a field like this, Module 11's encoding is not one option among several — it's the only defense that generalizes to unbounded, free-form input.

05Brain Exercise

Brain Exercise

A teammate wants to extend the allowlist idea to the guestbook's "name" field from Module 07: "Let's allowlist names to only letters, numbers, and spaces — that'll stop any XSS payload in that field completely, and we can drop the encoding call since it's redundant." Evaluate this plan.

The allowlist part is reasonable. Dropping the encoding call is the mistake — and it's the exact same mistake Decision #2 in this module's DECISIONS.md was written to prevent. A letters/numbers/spaces allowlist WOULD stop this specific payload shape. But it constrains a field that arguably shouldn't be that constrained in the first place — real names legitimately contain apostrophes (O'Brien), hyphens (Smith-Jones), and non-ASCII letters (José, Müller) — so the "safe" allowlist here is actually too strict for a name field, a real usability cost. Now suppose six months later, someone reasonably loosens the allowlist to permit apostrophes and accented characters, because real users are getting rejected. If the encoding call was removed on the theory that "validation already makes this safe," the fix that makes the field MORE usable simultaneously reopens the exact XSS bug this module exists to prevent — silently, with no compiler warning, because encoding wasn't there to catch what the loosened validation now allows through. This is precisely why Module 14's own `/allowlist` route keeps the encoding call even where it's currently redundant: validation rules change over time; the encoding call at the sink should never depend on today's validation rules staying exactly as strict as they are right now.

06There Are No Dumb Questions

Q: Is a blocklist ever appropriate for anything?
A: Blocklists can be a reasonable SECONDARY signal (flagging suspicious input for review, rate-limiting, logging) but should never be the sole security control for something as consequential as XSS prevention, precisely because they require anticipating every attack variant in advance — an inherently losing position against a determined attacker.
Q: What about numeric fields, like an "age" or "quantity"?
A: Those are actually a form of allowlisting too — "must parse as an integer between 0 and 150" is just as much an allowlist as "must be exactly 'asc' or 'desc'," just over a numeric range instead of a fixed set of strings. The same principle applies: define what's acceptable, reject everything else, regardless of what specific bad thing you can imagine.
Q: Does this module mean I should validate on the client side (in JavaScript) instead of the server?
A: Client-side validation is a UX nicety (instant feedback without a round-trip) but provides ZERO security value on its own — anyone can bypass client-side JavaScript entirely and send a raw request directly (exactly how this module's own curl commands worked, with no browser involved at all). Every validation check that matters for security must be enforced server-side; client-side validation, if present, is purely a convenience layered on top.
