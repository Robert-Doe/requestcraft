HTTP Request Anatomy

Before GET vs POST means anything, you need to see the bytes both of them actually are.

00Before You Start

Direct prerequisites for this module:

None — Module 01 is the start of the course
Before You Start You need to be comfortable with three things, and nothing more: running a command in a terminal (cd into a folder, run a script), the general idea that a browser and a server "talk" to each other somehow, and the fact that curl is a program that can send a web request from your command line instead of a browser. If any of those three feel shaky, this module is actually the right place to firm them up — you don't need to go anywhere first.

01The Big Analogy

Head First Moment

Picture a restaurant. Right now, forget the host, forget the waiter, forget the menu — forget everyone whose job is to understand what a customer wants. Just picture the doorbell camera above the front entrance. It doesn't know what a "reservation" is. It doesn't know what an "order" is. It just records exactly what arrives at the door — every word, every sound, completely unfiltered — and hands that raw recording to whoever asks for it.

That doorbell camera is what Module 01 builds. Before you ever write $_GET or req.body, you're going to be the doorbell camera: a program that listens on a port and prints exactly what a GET request and a POST request look like, byte for byte, before any framework has organized them into something friendlier.

GET — "What's on the menu?"

The customer stands in the doorway and asks a question out loud. Everyone nearby can hear it. Nothing in the kitchen changes because of it.

GET /menu?course=dessert HTTP/1.1

POST — "Here's my order"

The customer hands a sealed ticket to a runner, who carries it straight to the kitchen. The kitchen changes state — a dish gets made.

POST /order HTTP/1.1
  (ticket in the body)

Notice what the diagram is really showing you: both of these are just words arriving at a door. The only difference, at the raw level, is where the information lives — shouted publicly in the doorway (the URL) versus written on a ticket that gets carried in privately (the body). Nothing about GET or POST is magic. It's a convention about placement, and conventions can be violated. That single sentence is the seed of half the vulnerabilities you'll build and break in this course.

02What a Socket Actually Is

A socket (a numbered endpoint your operating system hands out so two programs on a network can exchange bytes) is the doorbell camera's actual hardware. When your browser or curl "sends a GET request," what really happens is: your OS opens a TCP connection to a port on the server, and then just... writes text into it. Plain text. No encryption by default, no special format beyond what both sides agree to interpret as HTTP.

The text your browser writes for a GET request looks almost exactly like what you'd type if you opened the socket by hand:

GET /search?q=hello HTTP/1.1
Host: localhost:8000
User-Agent: curl/8.12.1
Accept: */*

And for a POST request, the only structural difference is that there's now a blank line followed by a body — the sealed ticket handed to the kitchen:

POST /comment HTTP/1.1
Host: localhost:8000
Content-Type: application/x-www-form-urlencoded
Content-Length: 20

name=bob&message=hi
Why this matters Every "hidden" thing a POST request does is only hidden from the URL bar and browser history — it is not hidden from the network, from the server's memory, or from anyone who can read the raw bytes, exactly as you're about to do yourself. That distinction — hidden from casual view vs. actually protected — is one you'll rely on constantly once you get to CSRF and cookie security later in this course.

03Building the Raw Listener

Here's the core of node/raw_server.js — the doorbell camera itself. Every line that isn't a trivial assignment has a comment explaining why it's there, not just what it does:

const net = require('net'); // Node's raw TCP module -- one level below 'http'

const PORT = 8000;              // arbitrary unprivileged port
const READ_BUFFER_BYTES = 8192; // 8 KB -- plenty for this course's tiny demo requests

function handleConnection(socket) {
  socket.on('data', (chunk) => {
    const raw = chunk.toString('utf8'); // Buffer -> string, purely so we can print it

    console.log('--- RAW BYTES RECEIVED ---');
    console.log(raw);                 // print it completely unparsed -- that's the whole point
    console.log('--- END ---\n');

    socket.write(                     // minimal response so curl doesn't hang
      'HTTP/1.1 200 OK\r\n' +
      'Content-Type: text/plain\r\n' +
      'Content-Length: 5\r\n' +
      '\r\n' +
      'seen\n'
    );
    socket.end();                     // one request per connection at this stage
  });
}
Why this matters Look closely at chunk.toString('utf8'). That line is a decision, not a formality — it assumes the bytes are UTF-8 text. A real HTTP body can be binary (an uploaded image, for instance), and a real parser has to know when it's safe to treat bytes as text and when it isn't. You'll see this exact assumption become load-bearing again in Module 15 (File Upload Abuse).

The full file — including the "only one connection at a time" logic — lives in node/raw_server.js, fully commented per line. The PHP equivalent, php/raw_server.php, does the identical job with stream_socket_server() and fread(); it's real, complete code, ready the moment you install PHP.

A small but real contrast between the two runtimes

The Node version needs an explicit acceptingConnections flag to stop two clients being handled at once, because Node's socket model is event-driven by default — it would happily interleave two clients' output if you let it. The PHP version gets the same "one at a time" behavior for free, because stream_socket_accept() blocks until a client connects and the script simply doesn't call it again until the current one is closed. Same observable behavior, two completely different reasons — a preview of a theme that will keep recurring as this course compares PHP and Node.

05Brain Exercise

Brain Exercise

Open two extra terminals. In Terminal A, type (but don't press Enter yet):

curl "http://localhost:8000/first"

In Terminal B, type (but don't press Enter yet):

curl -X POST "http://localhost:8000/second" -d "x=1"

Now press Enter in Terminal A, then immediately press Enter in Terminal B, as fast as you can. Which raw request do you expect to see printed first in your server's terminal — /first or /second?

Most people say "/first, obviously — I pressed Enter on it first." But TCP connection acceptance is decided by your operating system's network stack, not by which terminal you typed into first or even which curl process started first. The OS queues incoming connection attempts and hands them to accept() in the order it received them — which depends on process scheduling, DNS/loopback resolution timing, and OS-level buffering, none of which you control from your keyboard. Run it a few times: you will occasionally see /second printed first, even though you swear you pressed Enter on Terminal A first. This is the exact same reason production servers never assume request order reflects client intent — a lesson that resurfaces hard in Module 09 and 10 (CSRF), where an attacker deliberately exploits the fact that a server can't tell who or in what order requests were meant to arrive.

06There Are No Dumb Questions

Q: Isn't this exactly what $_GET / req.query already do for me? Why not just start there?
A: Because $_GET and req.query are trust decisions someone already made on your behalf — they've decided the query string is UTF-8 text, decided how to split on & and =, decided how to percent-decode it. You're about to spend an entire course reasoning about when those decisions go wrong (that's what XSS is). You can't audit a decision you've never seen made.
Q: My browser's request looked way longer than curl's when I checked DevTools. Did I do something wrong?
A: No — browsers attach a lot more headers by default (Cookie, Accept-Language, Accept-Encoding, Sec-Fetch-*, a much longer User-Agent). Both are still perfectly valid GET requests; curl is just a much more minimal client. The method line and the overall shape (headers, blank line, optional body) are identical.
Q: If POST "hides" the data from the URL, doesn't that mean POST is more secure?
A: This is the single most common misconception in web security, and you just disproved it yourself — you watched the POST body print out in plain text in your own terminal. POST only hides data from the URL bar, browser history, and server access logs. It does nothing for confidentiality on the wire (that's TLS's job) and nothing to stop anyone with your source code, your terminal, or a network capture from reading it. Keep this experiment in mind every time someone claims "we use POST so it's safe."
Q: This all feels like plumbing. Where does XSS actually come in?
A: Right here, structurally. XSS happens when data that arrived in either of the two places you just saw — the URL's query string or the POST body — gets written back into an HTML page without being re-encoded for that context. You cannot spot that bug reliably until you know, precisely, where in the raw request that data lived and how it got from there into your server's memory. Module 02 takes these exact bytes and shows you the parsed version; Module 05 is where you'll break it.
