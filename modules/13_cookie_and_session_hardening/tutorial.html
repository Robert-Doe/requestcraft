Cookie & Session Hardening

The script still runs. This time, it finds an empty pocket.

00Before You Start

Direct prerequisites for this module:

Module 07 — Stored XSS via POST
Before You Start You need Module 07's stored-XSS mechanic solid, and you should already suspect that a script running in a victim's browser could do more than change a page title — it could read anything else that page has access to. This module makes that concrete: your session cookie.

01The Big Analogy

Head First Moment

Your session cookie is the loyalty card from Module 09 — the thing that proves "this browser is currently you" to the bank. So far, every attack targeted the KITCHEN. This module targets your wallet directly: if a fake announcement (an injected script) can be read aloud in your restaurant, it can also just as easily read the number off your loyalty card out loud to a stranger standing nearby — not because the stranger asked the waiter, but because the announcement itself was written to do exactly that. HttpOnly is a special kind of wallet that physically cannot be opened by anyone standing at the counter, announcement or not — only the bank's own back-office systems can ever see what's inside it.

02What Actually Happened, Verified

vulnerable-cookie

document.cookie returned "session=SECRET-abc123". The injected script exfiltrated it. The attacker's collector logged the real secret.

fixed-cookie

document.cookie returned "" — empty. The identical script still ran and still fired its beacon. The collector logged an empty string.

The only code difference between the two servers is this header:

// vulnerable-cookie:
res.setHeader('Set-Cookie', 'session=SECRET-abc123; Path=/');

// fixed-cookie:
res.setHeader('Set-Cookie', 'session=SECRET-abc123; Path=/; HttpOnly; SameSite=Lax');
Verified This course actually stole a cookie and confirmed it in the attacker's own server log: [COLLECTOR] received cookie value: "session=SECRET-abc123". Against the hardened server, the identical payload, the identical attacker page, logged: [COLLECTOR] received cookie value: "".
Why this matters Notice exactly what did NOT change between the two tests: the stored-XSS bug. The injected <script> ran successfully both times — you can confirm this because the beacon request reached the collector both times. HttpOnly doesn't stop the attack from executing. It stops the ONE PIECE of that attack — reading this specific cookie via JavaScript — from succeeding, categorically, at the browser level, no matter how the script got there or what it's written to do.

04Brain Exercise

Brain Exercise

A teammate says: "If HttpOnly stops JavaScript from reading the cookie, then an XSS bug on a site using HttpOnly cookies is basically harmless now, right?" What's missing from this conclusion?

The injected script can still do everything else it could always do — it just can't read this one specific cookie by name. An XSS payload running in the victim's browser can still: submit forms as the victim (CSRF-style, but from INSIDE the trusted page, bypassing the origin checks Modules 09-10 relied on), make authenticated requests to the same site's API using the browser's automatically-attached cookies (the request still carries the HttpOnly cookie — HttpOnly blocks JAVASCRIPT from reading it, not the BROWSER from sending it on legitimate same-origin requests), read and modify anything else on the page, log keystrokes, redirect the user to a phishing page, or read any OTHER cookie that isn't marked HttpOnly. Stealing the raw session token is just the single most dramatic outcome — HttpOnly closes exactly that one door and leaves the house's front door (the XSS bug itself) wide open. This is precisely why Module 11's fix is not optional just because a cookie is hardened.

05There Are No Dumb Questions

Q: If HttpOnly cookies still get sent on requests the malicious script makes, what's actually protected?
A: What's protected is the raw secret VALUE leaving the browser in a form the attacker can read and reuse independently — for instance, pasting it into their own browser's cookie jar to impersonate the victim from a completely different machine, at a time of their choosing, even after the XSS bug is later patched. Without HttpOnly, the attacker owns a portable copy of your session. With it, any damage is limited to what the injected script can do live, in the victim's own browser, in that moment.
Q: Does HttpOnly protect against CSRF?
A: No — and this is a common mix-up. CSRF (Modules 09-10) works precisely BECAUSE the browser attaches cookies automatically to legitimate cross-site requests, regardless of HttpOnly. HttpOnly only restricts JavaScript's ability to READ a cookie's value; it has no effect on whether the browser SENDS that cookie on a request. SameSite is the flag that addresses CSRF, which is why Module 10's fix used SameSite, not HttpOnly.
Q: Should EVERY cookie be HttpOnly?
A: No — only cookies that don't need to be read by your own legitimate JavaScript. A cookie storing a non-sensitive UI preference (like "dark mode: on") that your own script legitimately needs to read has no reason to be HttpOnly. Session tokens, auth tokens, and anything whose theft would let someone impersonate the user should always be HttpOnly; that's specifically what this flag is for.
