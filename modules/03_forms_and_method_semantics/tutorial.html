Forms & Method Semantics

Watch your own address bar tell the truth about where GET and POST data actually lives.

00Before You Start

Direct prerequisites for this module:

Module 02 — Superglobals & req Objects

01The Big Analogy

Head First Moment

Picture the dining room itself. When you ask the host a question out loud — "what desserts do you have?" — everyone at the nearby tables hears it, and if the restaurant kept a guestbook of everything said in the dining room, your question would be written down in it. That's a GET form: whatever you type goes straight into the address bar, in public, in a place your browser's history and the server's access log both record.

Now picture handing a folded ticket directly to a runner, who walks it straight to the kitchen without reading it aloud. Nobody in the dining room heard it, and the guestbook has no record of what was on it — only that a ticket was handed in. That's a POST form.

GET form

Submitting adds ?q=your+text to the address bar. You can bookmark the result. It's in your browser history.

<form method="get" action="/search">

POST form

Submitting leaves the address bar showing only /comment. Nothing you typed appears there, ever.

<form method="post" action="/comment">

02The HTML That Makes the Difference

The entire behavioral difference you're about to see comes down to one attribute. Here's the actual markup from this module's demo page:

<form method="get" action="/search">   <!-- browser builds ?q=... and navigates to it -->
  <input name="q" placeholder="search term">
  <button type="submit">Search (GET)</button>
</form>

<form method="post" action="/comment"> <!-- browser sends the value in the body instead -->
  <input name="message" placeholder="leave a message">
  <button type="submit">Post (POST)</button>
</form>

Nothing else in the page changes this behavior — no JavaScript is involved. The browser itself decides, purely from the method attribute, whether to encode your input into the URL or into a hidden body.

Why this matters Because this is pure browser behavior with no script involved, it also means a GET form can be triggered by things that aren't you clicking a button — a prefetch, a crawler following a link, even a browser extension pre-loading pages it thinks you'll visit next. You'll see exactly why that matters in Module 04 (Idempotency & Safety) and Module 09 (CSRF via GET).

03What the Server Actually Logs

This module's server prints a line for every request, styled exactly like a real access log entry:

function accessLogLine(method, path, queryString) {
  const url = queryString ? `${path}?${queryString}` : path; // query string included if present
  return `[ACCESS LOG] ${method} ${url}`;      // POST body is NEVER part of this -- there's nowhere for it to go
}

Submit the GET form and you'll see [ACCESS LOG] GET /search?q=hello printed to the terminal. Submit the POST form and you'll see only [ACCESS LOG] POST /comment — your message is nowhere in that line, because it was never part of the URL to begin with.

05Brain Exercise

Brain Exercise

After submitting the GET form once, click your browser's Back button, then click Forward again. Now try refreshing the page (F5) while you're on the /search?q=hello result. Does anything different happen compared to refreshing the /comment result after a POST?

Refreshing the GET result just re-runs the search silently. Refreshing the POST result, in most real browsers, pops up a warning like "Confirm Form Resubmission." This isn't a random browser quirk — it's the browser enforcing the exact safety rule from RFC 7231 that Module 04 names explicitly: GET is supposed to be safe to repeat with no side effects, so silently re-running it is fine. POST is assumed to change state (place an order, post a comment), so the browser refuses to silently repeat it without your explicit confirmation — because doing so might, for example, submit your comment a second time. You just watched your browser encode a security-relevant assumption about GET vs. POST into its UI, without any code from this module doing it for you.

06There Are No Dumb Questions

Q: Can I make a GET form submit without the query string showing in the URL?
A: Not with a plain HTML form — that's the browser's built-in behavior for `method="get"`, not something the page controls. You could intercept the submission with JavaScript and send the request a different way (Module 08 territory), but then it's no longer really "a GET form" in the way this module means it — it's a script deciding to make its own request.
Q: Does using POST mean my message is encrypted or hidden from anyone snooping on the network?
A: No — and this is worth repeating from Module 01: POST only hides data from the address bar, browser history, and access logs. Anyone capturing raw network traffic sees the POST body in plain text just as easily as a GET query string, unless the connection uses TLS (`https://`), which is a completely separate mechanism this course doesn't set up (see Module 01, Decision 5).
Q: Why did the tutorial say a GET form "can be triggered by things that aren't you clicking a button"? A form needs a click, doesn't it?
A: A `
` needs a click, yes — but the equivalent underlying HTTP request doesn't need a form at all. An `` tag makes the exact same GET request the browser would make for you, with zero clicks, the instant the page containing that image tag loads. That's not a form being submitted — but it's indistinguishable from one on the wire, and it's the exact mechanism behind Module 09's CSRF-via-GET attack.
