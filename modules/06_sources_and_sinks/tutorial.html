01The Big Analogy

Head First Moment

Module 05 showed you one door into the restaurant (the front entrance, where GET requests walk in) and one dangerous room (the PA system, which reads announcements aloud to everyone). But a real restaurant has more than one door — the delivery entrance around back (POST bodies), the comment card box by the register (cookies), even the note a delivery driver scrawls on the receipt (the Referrer header). And it has more than one dangerous room — the specials board everyone reads (innerHTML), the intercom to the kitchen (document.write), a photocopier that blindly executes whatever's written on a page fed into it (eval).

A source is any door untrusted data can walk in through. A sink is any room where, if that data arrives without being clearly marked "this is just something someone said, not an instruction," something dangerous can happen. Module 06 is the floor plan of the whole building.

02Building the Classifier

Rather than just memorizing that table, Module 06 has you build a tiny program that applies it. Here's the core decision logic from node/analyze.js:

function classify(line) {
  const sourceHit = SOURCES.find((s) => s.pattern.test(line));
  const sinkHit = SINKS.find((s) => s.pattern.test(line));
  const escaped = ESCAPE_MARKERS.test(line);

  if (sourceHit && sinkHit && escaped) {
    return 'SAFE (escaping call seen before the sink)';
  } else if (sourceHit && sinkHit) {
    return 'DANGEROUS (source flows into a sink, unescaped)';
  }
  // source-only or sink-only lines fall through here -- see the full file
}
Why this matters Notice the classifier needs THREE pieces of information to reach a verdict, not two: a source, a sink, AND whether escaping happened in between. Most people, after Module 05, remember "sinks are dangerous" but forget that a source reaching a sink is only half the story — the other half, escaping, is exactly what Module 11 is going to teach you to do properly.

03What the Classifier Actually Found

Two of the ten samples are worth reading closely. First, the exact bug from Module 05:

echo "<p>You searched for: {$_GET['q']}</p>";
→ SOURCE: $_GET   SINK: echo   VERDICT: DANGEROUS

And a line where the SAME source and SAME sink appear, but escaping happened first — during a variable assignment, one statement before the `echo`, not inline at the `echo` itself:

$name = htmlspecialchars($_POST['name']); echo "<p>Hi, $name</p>";
→ SOURCE: $_POST   SINK: echo   VERDICT: SAFE (escaped)

Both lines have a source and a sink. Only the presence of htmlspecialchars() somewhere between them changes the verdict — which is the entire lesson of Module 06 in two lines of code.

05Brain Exercise

Brain Exercise

The classifier printed this verdict for one sample:

$stmt->bindParam(':q', $_GET['q']);
→ SOURCE: $_GET   VERDICT: source only -- no dangerous sink matched (likely fine here)

Does "no XSS sink matched" mean this line is completely safe to ship?

No — it means this line is safe from XSS specifically. It says nothing about SQL injection. bindParam is a parameterized-query API, which IS the correct defense against SQL injection — but that's a completely different vulnerability class with its own sources and sinks (here, the "sink" would be raw SQL string concatenation, not HTML rendering). This module's classifier was built with exactly one job: flag XSS-relevant flows. A clean verdict from this tool is not a clean bill of health for the whole line — it's a clean bill of health for the one category of bug this tool was built to catch. Real security reviews run multiple specialized lenses over the same code for exactly this reason.

06There Are No Dumb Questions

Q: Is document.cookie always dangerous to read?
A: Reading `document.cookie` isn't dangerous by itself — it becomes a source of concern when that cookie value then flows into a sink (e.g. logging it somewhere an attacker can read, or writing it into the DOM). Module 13 (Cookie & Session Hardening) covers the flip side: making sure your MOST sensitive cookies (session tokens) can't even be read by JavaScript at all, via the `HttpOnly` flag — removing them as a source entirely.
